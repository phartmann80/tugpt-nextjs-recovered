# ADR-013: Docker Compose Deployment on the Existing VPS (Replacing Vercel)

## Status
Accepted

## Context
The repository's `vercel.json`, `apps/web/README.md`, and the default `create-next-app` scaffolding all assumed the web app would deploy to Vercel. In practice, no `tugpt-nextjs-recovered` project exists under the connected Vercel account, and the account is being moved away from. TuGPT already has a production home: the dedicated VPS at `212.227.44.13`, which currently runs `tugpt-whatsapp-worker` and `tugpt-draft-worker` as systemd-native Node processes reading secrets from `/etc/tugpt/worker.env`. This ADR is about containerizing that existing setup and adding the web app to the same server — not about picking a new server. (An earlier draft of this ADR incorrectly assumed a shared VPS at a different IP; that was a mix-up and has been corrected.)

The workers were never deployable via Vercel in the first place (Vercel doesn't run long-lived background processes), so they've always needed exactly this kind of always-on host. This ADR formalizes the web app moving to the same host, and turns the deployment mechanism for all three processes into something explicit and reviewable in code, rather than done by hand on the server.

## Decision
1. **Runtime**: Docker Compose (`docker-compose.yml` at the repo root) defines three services — `web`, `whatsapp-worker`, `draft-worker` — built from `apps/web/Dockerfile` and `apps/worker/Dockerfile` respectively. The two worker services share one image and differ only by `command:` (`dist/index.js` vs `dist/draft-index.js`), matching the existing constraint that these must run as separate processes (see `apps/worker/src/draft-index.ts` header comment).
2. **Web build**: `apps/web/next.config.mjs` sets `output: 'standalone'` and `outputFileTracingRoot` to the monorepo root, so the Docker image ships only the traced runtime files rather than the full monorepo `node_modules`.
3. **Supervision**: A systemd unit (`deploy/systemd/tugpt.service`) wraps `docker compose -p tugpt up -d` / `down`, giving reboot-safety and `systemctl` ergonomics without needing a bespoke unit per process. Docker Compose owns process supervision (restart policy `unless-stopped`) within the stack; systemd owns "start the stack on boot." This unit replaces `tugpt-whatsapp-worker.service` and `tugpt-draft-worker.service` — see the cutover plan in `docs/production_environment.md` section 5.4. Those units must be stopped and disabled as part of cutover, not left running alongside the containers; both would poll the same PGMQ queues and double-process jobs.
4. **Graceful shutdown**: `stop_grace_period` is set explicitly per worker in `docker-compose.yml` (30s for `whatsapp-worker`, 90s for `draft-worker`), because SIGTERM only breaks the poll loop between jobs (see `apps/worker/src/draft-worker.ts`) and does not cancel an in-flight job. At the time this ADR was written, a draft job could chain through three providers at up to 25s each (~75s worst case); as of the 2026-08-18 single-provider decision (see ADR-006), that worst case is ~25s, but the 90s figure is kept as a conservative margin rather than tightened here — this ADR is about the deployment mechanism, not provider architecture. Either way, it exceeds Docker's default 10s SIGTERM→SIGKILL grace period; without this, cutover would reintroduce a regression versus the systemd-native workers' verified graceful shutdown behavior.
5. **Secrets**: Environment variables are not baked into images or committed to git. Each service's `env_file` points at a root-owned file under `/etc/tugpt/` on the host (`web.env`, `worker.env`). `worker.env` already exists on `212.227.44.13` and is reused as-is; `web.env` is new, since the web app has never run on this server before.
6. **CI validation**: `.github/workflows/ci.yml` gained a `docker-build` job that builds both images on every push/PR, since there is no Docker daemon available to build-test these Dockerfiles outside of CI/the VPS itself. Both jobs passed on the PR that introduced them.
7. **Explicitly out of scope for this ADR**: Logicc credential configuration and enabling `whatsapp_integration` remain untouched — this is a deployment-mechanism change only, not a feature-flag or provider-credential change.

## Consequences
- **No more Vercel assumptions**: `vercel.json` is removed; `apps/web/README.md` points at this ADR and `docs/production_environment.md` instead of the Vercel platform.
- **Single source of truth during cutover**: the systemd-native and containerized workers must never run concurrently. `docs/production_environment.md` section 5.4 gives an explicit stop-then-start sequence rather than a gradual migration, plus a verification step (confirm each side's poll-loop log line appears exactly once) before treating cutover as complete.
- **Rollback path**: `tugpt-whatsapp-worker.service` / `tugpt-draft-worker.service` are disabled, not deleted, immediately after cutover — kept on disk as a fallback until the compose stack has proven stable in production.
- **Manual verification still required for the images themselves**: no Docker daemon was available in the environment that authored these Dockerfiles; they're validated by the new CI job (both builds passed) rather than a real `docker run` against production Supabase/provider credentials. The first real deploy is the actual integration test for that part.
- **Pre-deploy security checklist**: `docs/production_environment.md` section 5.2 adds explicit checks (SSH key auth / password auth disabled, `ufw` scoped to 22/80/443, no application port bound to `0.0.0.0`, Docker not bypassing `ufw`) to confirm against the real state of `212.227.44.13` before cutover, since this ADR changes what's listening on that host.
